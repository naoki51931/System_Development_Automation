# Notifications, email, documents, and project chat

## Local-only safety boundary

This phase uses local PostgreSQL, `LocalArtifactStorage`, `MockNotificationProvider`, `MockEmailProvider`, and `MockAIProvider` only. SES, SMTP, external push, external AI, AWS S3, RDS, Stripe, Terraform, ECS/ECR, public WebSockets, and real customer communication remain disabled. Future provider credentials must be obtained from Secrets Manager at runtime and never persisted.

## Notification preferences and delivery

Preferences are unique by organization, user, and event type. IANA timezones are validated with the standard timezone database. Quiet hours support both same-day and overnight ranges. Immediate, hourly, daily, and none digest modes compute a UTC `scheduled_at`.

Security events such as payment failure, maintenance suspension, and deletion scheduling always retain in-app delivery and cannot be changed to digest none. Critical notifications also write sanitized audit logs.

Notifications use a tenant/user-scoped deduplication key. The title and body are plain text with secret patterns removed. Action URLs must begin with one slash and cannot be external, protocol-relative, JavaScript, or contain backslashes. Deletion is logical through status; PostgreSQL blocks hard deletion.

Deliveries support in-app and email channels, bounded attempts, failure codes, and an exponential-backoff `scheduled_at`. Push and SMS are not implemented.

## Email templates and providers

`EmailProvider` exposes send, status, and connection checks. Only `MockEmailProvider` is enabled. SES and SMTP implementations are network-disabled stubs.

Organization-approved templates override approved system defaults. Template expansion accepts only simple `{{ variable_name }}` placeholders from a fixed allowlist. Blocks, expressions, imports, attribute traversal, code execution, external URLs, and file references are rejected. Values are escaped, HTML is sanitized, scripts/event attributes/references are removed, and secrets are redacted.

The idempotent seed includes:

- estimate submitted/approved;
- contract activated;
- payment succeeded/failed;
- maintenance past due/suspended;
- artifact review requested/changes requested/approved;
- deployment completed;
- deletion scheduled;
- chat message received.

Approved templates cannot be updated; a new `version_number` is required.

Each `email_messages` row has exactly one recipient and immutable recipient/content snapshots. It stores no BCC list, SMTP password, access key, card data, JWT, database URL, or raw provider response. Subjects reject CR/LF header injection. Deduplication keys prevent resending.

## Documents and PDF generation

Document templates are resolved organization first, then system default. JSON payloads are checked against a restricted object schema with required fields, declared properties, primitive type checks, and no external references. Template storage keys remain behind ArtifactStorage path validation.

Implemented local outputs are HTML, Markdown, and PDF. DOCX/XLSX remain modeled interface outputs but return a controlled not-implemented error. PDF bytes are generated inside the process without a browser, JavaScript, URL fetcher, file loader, font download, or external service.

Implemented documents:

- approved estimate: authoritative number, organization, project, dates, DB line items, subtotal, tax, total, currency, and notes;
- contract: authoritative contract/estimate values, terms version, acceptors/timestamps, and start time;
- basic design: cover, overview, purpose, users, architecture, screens, APIs, tables, review policies, non-functional requirements, and revision history; missing facts are explicitly `未設定`.

The request never supplies authoritative totals. Generated bytes are stored under a server-generated tenant key. Every generation creates a new artifact and immutable artifact version, with SHA-256, size, and a completed generation job. The tuple of authoritative payload hash, document type, template, and output format is idempotent.

Document email sends an opaque expiring download URL rather than the file or storage key. Only the approved current artifact version may be sent. The same transaction updates the notification, notification delivery, and one-recipient email snapshot.

## Project chat

Rooms belong to one organization and project and may be project, support, review, or maintenance rooms. Active project membership or privileged project/organization roles are required. Archived and closed rooms reject posts.

Human posts cannot claim the AI or system message type. AI messages have a null human sender and an explicit `ai` type. Bodies are limited to 10,000 characters, converted to safe plain text, stripped of script/HTML, and secret-redacted. Edit uses optimistic locking; deletion replaces content and records `deleted_at`. PostgreSQL rejects physical deletion.

Attachments reference existing immutable artifact versions. The service verifies tenant/project ownership and uses ArtifactStorage `head_object` to compare MIME, size, and SHA-256 before registration.

## Change requests

A chat message can create a scoped change request and optionally link an additional estimate from the same tenant/project. MockAI produces a bounded impact row and then moves the request to human/customer approval; it never activates a contract, starts development, or creates a payment.

Major change, new feature, and infrastructure scopes require saved impact analysis before approval. Only a customer or organization administrator can approve. The originating chat, estimate link, analysis rows, approver, and timestamps remain stored. Impact rows are append-only.

## Outbox and event integration

Outbox uniqueness covers organization, event type, aggregate, aggregate ID, and payload hash. A processed event is a no-op on replay. Failure increments attempts and moves `available_at` with exponential backoff.

Integrated events include estimate submission/approval, contract activation, payment success/failure, maintenance past due/suspension, artifact review/change/approval, chat messages, document generation, and change request submission/approval. Notification deduplication is separate from outbox uniqueness, preventing duplicate notification and email rows even when handlers retry.

No external message queue is used in this phase.

## Security summary

- tenant and project authorization before reads/writes/download URLs;
- logical deletion and immutable/append-only database triggers;
- header-injection, XSS, Markdown/HTML, SSRF, external URL, JavaScript, and path traversal controls;
- MIME, file size, and content-hash attachment checks;
- email address is never emitted to application logs;
- secrets, JWTs, database URLs, API keys, and card data are redacted from messages and documents;
- raw template source, local paths, storage keys, SQL, and internal exceptions are not returned by APIs.
